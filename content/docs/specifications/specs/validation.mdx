## Requirements

- `opentide validate` MUST run default checks: `id-uniqueness`, `uuid-format`, `schema`.
- Schema validation MUST load each object via `metadata.schema` and validate against the registered Pydantic model.
- Vocabulary validation MUST walk metaschema `tide.vocab` annotations for each object type.
- UUID values MUST be UUID version 4.
- Object UUIDs MUST be unique across the workspace registry.
- Cross-object references MUST resolve to existing objects when checked.
- Threat `chaining` relationships MUST reference valid targets when checked.
- Query validation MUST only be offered for platforms in the query-validation allowlist (see [platforms/index.md](/docs/specifications/specs/platforms/)).
- Platforms without query validators MUST return `supported: false` — not fake success.
- The schema check MUST report `external_id_in_rule` for `rule_id`, `rule_id_bundle`, or `rule_id::<tenant>` at the root of any platform block and MUST suppress the redundant generic unknown-key diagnostic for that same field.
- Full-workspace validation MUST validate every deployment-state shard under `.opentide/states/deployment/`, including orphan shards whose `object_uuid` is not in the registry. A missing shard is not an error.

## Definition

### Check types (`ValidateCheck`)

| Check | Identifier | Default | Description |
|-------|------------|---------|-------------|
| ID uniqueness | `id-uniqueness` | yes | No duplicate `metadata.uuid` across YAML files |
| UUID format | `uuid-format` | yes | Every UUID must be valid UUIDv4 |
| Schema | `schema` | yes | Pydantic model validation + vocab + cross-ref |
| CVE | `cve` | no | CVE reference integrity (optional flag) |
| Sharing config | `sharing-config` | no | `sharing.toml` integration blocks: required keys, unique names, known keys, `max_tlp`, `object_types`, and `organisation_uuid`. On for `opentide share push`. |

### Schema check sub-steps

When `schema` is enabled, for each in-scope object the implementation MUST, in order:

1. **Load and model-validate** — resolve the object's `metadata.schema` and validate it against the registered model.
2. **Vocabulary** — check controlled-vocabulary fields against the indexed metaschema vocabulary annotations.
3. **Deprecation** — flag deprecated fields as warnings.
4. **References** — resolve `references` links to existing objects.
5. **Chaining** — resolve chaining relationships (threat vectors only).

The model-validation step reports a legacy external-id key as `external_id_in_rule` rather than as an unknown key ([platforms/index.md](/docs/specifications/specs/platforms/#external-rule-ids)). The key is checked at the root of every platform block only; a key of the same name nested inside `alert`, `query`, `exclusions`, or another field is not a legacy key.

Steps 4 and 5 resolve cross-object links; they run whenever the `schema` check runs against a full workspace scope where the referenced objects are present.

### Validation scope

| Mode | Behavior |
|------|----------|
| `full` | All objects in the workspace index |
| `narrow` | Filter by `--file`, `--uuid`, and/or `--type` |

When `--file`, `--uuid`, or `--type` filters match no objects, validation MUST emit a `scope_no_match` error rather than silently passing — a filter that selects nothing is treated as a mistake, not a success. With several `--file` targets, validation MUST fail when any one of them matches no object, even if the others do. The production write-back relies on this to commit only rule files that were actually validated ([deployment-state.md](/docs/specifications/specs/deployment-state/#continuous-integration)).

### Deployment state

In `full` scope, validation MUST read every `*.json` file under `.opentide/states/deployment/` and report the [deployment-state](/docs/specifications/specs/deployment-state/#diagnostics) codes: `deployment_state_shape`, `deployment_state_platform`, and `deployment_state_uuid_mismatch` (including two files that canonicalise to one uuid). Orphan shards are validated like any other. A rule with no shard is not an error. `narrow` scope MAY check only the shards of the selected rules plus any shard file passed directly.

| Code | Severity | When |
|------|----------|------|
| `external_id_in_rule` | error | A legacy external-id key at the root of a platform block |
| `deployment_state_shape` | error | A shard is unreadable or violates `deployment.state::1.0` |
| `deployment_state_platform` | error | A shard names a platform that is not state-backed |
| `deployment_state_uuid_mismatch` | error | A shard's filename and `object_uuid` disagree or are not lowercase canonical |

### Query validation

Command: `opentide validate query --platform <id> --live`

| Platform | Supported |
|----------|-----------|
| `sentinel` | yes |
| `defender_for_endpoint` | yes |
| `splunk` | yes |
| `sentinel_one` | yes |
| `carbon_black_cloud` | yes |
| `elastic` | yes, live only: Kibana rule preview and the Elasticsearch checks ([elastic-1.0](/docs/specifications/specs/platforms/elastic-1.0/#query-validation)) |
| `crowdstrike` | no |
| `harfanglab` | no |

Requires platform credentials and enabled configuration. Validates deployed or planned rule queries against the live platform API. Query validation is a tenant check on every platform in the query-validation allowlist above: without `--live` the command MUST refuse and name `--live`, and MUST NOT report a pass. `crowdstrike` and `harfanglab` report `supported: false` instead ([platforms](/docs/specifications/specs/platforms/#query-validation-platforms)). No platform has an offline syntax check; Elastic's query language (KQL, Lucene, EQL, or ES|QL) comes from each rule's block: its `type`, and `language` for the types that take one.

Deployment fixtures (`scripts/deployment_state_fixtures.py`) are checked against [schemas/deployment.state.1.0.schema.json](https://github.com/opentidehq/specifications/blob/main/schemas/deployment.state.1.0.schema.json) plus the filename rules the schema cannot see. Each invalid shard fixture is checked under the shard filename the checker assigns to it (a uuid that differs from `object_uuid` for `uuid-mismatch.json`, the uppercase spelling for `noncanonical-uuid.json`, the valid name otherwise). The valid shard must be byte-identical to writer output, and no rule fixture in `fixtures/valid/`, `fixtures/platforms/`, or `fixtures/cross-object/` may carry a legacy external-id key.

Sharing fixtures (`scripts/sharing_fixtures.py`) also prove the merge rule: [override.toml](https://github.com/opentidehq/specifications/blob/main/fixtures/sharing/valid/override.toml) merged by `name` onto [sharing.toml](https://github.com/opentidehq/specifications/blob/main/fixtures/sharing/valid/sharing.toml) MUST equal [merged.toml](https://github.com/opentidehq/specifications/blob/main/fixtures/sharing/valid/merged.toml).

On a rule's `configurations.elastic` block the checker applies three of the [Elastic constraint codes](/docs/specifications/specs/platforms/elastic-1.0/#constraints), the ones the invalid Elastic fixture exercises: `language`, `esql_source`, and `suppression_shape`. They are the platform's own codes, so the checker and `opentide validate` report the same name. The other Elastic codes, and every other platform block, are left to opentide.

A packed semicolon string that happens to start with a valid token MUST still fail `packed_vocab_string`. Accepting only the first token is lossy and non-compliant.

### Issue severities

| Severity | Examples |
|----------|----------|
| `error` | Schema failure, duplicate UUID, invalid UUID, broken cross-ref, `external_id_in_rule`, invalid deployment-state shard |
| `warning` | Deprecated field usage |

### Environment signals

| Variable | Set when |
|----------|----------|
| `VALIDATION_ERROR_RAISED` | One or more errors |
| `VALIDATION_WARNING_RAISED` | One or more warnings |

### Parallel execution

Validation MAY parallelize per-object work and ID scans; worker count is resolved from object count and optional `--workers` flag.
